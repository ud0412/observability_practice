# 06 설명 — 왜 Alloy를 두 방식으로 배포하나요?

Alloy는 관측 데이터를 모아 저장 도구로 보내는 수집기입니다. 이번 실습에서는 노드마다 하나씩 실행하는 Alloy와, 애플리케이션이 데이터를 보내는 중앙 Alloy를 사용합니다.

**노드 Alloy를 DaemonSet으로 배포하는 이유:** 노드 CPU·메모리 정보와 컨테이너 로그 파일은 각 노드에서 읽어야 합니다. DaemonSet을 사용하면 대상 노드마다 수집기가 하나씩 실행됩니다. control-plane과 worker에 각각 하나, 총 두 개가 실행됩니다.

노드 Alloy는 자체 unix exporter로 노드 메트릭을 수집하고, Kubernetes의 cAdvisor 정보로 컨테이너 사용량을 수집합니다. 로그는 자신이 실행 중인 노드의 파일만 읽어 중복 수집을 피합니다.

**중앙 Alloy를 두는 이유:** Spring Boot와 FastAPI는 메트릭·트레이스를 네트워크로 보냅니다. 두 서버가 같은 수신 주소를 사용하도록 중앙 Alloy를 Deployment로 실행합니다. 중앙 Alloy는 애플리케이션 메트릭을 Mimir로, 트레이스를 Tempo로 전달합니다.

트레이스에 중앙 수집기가 반드시 필요한 것은 아닙니다. 이번 과정에서는 전달 경로와 설정을 한곳에서 배우기 위해 선택한 구성입니다.

| 수집 데이터 | 담당 | 저장 도구 |
|---|---|---|
| 노드·컨테이너 메트릭 | 노드 Alloy | Mimir |
| 컨테이너 stdout 로그 | 노드 Alloy | Loki |
| 서버 자동 계측 메트릭 | 중앙 Alloy | Mimir |
| 서버 자동 계측 트레이스 | 중앙 Alloy | Tempo |

Alloy의 메트릭 WAL과 로그 읽기 위치는 디스크에 유지합니다. 아직 전송하지 못한 메모리 속 데이터까지 모두 영구 보관되는 것은 아닙니다. kind의 두 노드는 같은 WSL 커널 자원을 공유하므로 별도 물리 서버처럼 사용량을 합산하지 않습니다.
